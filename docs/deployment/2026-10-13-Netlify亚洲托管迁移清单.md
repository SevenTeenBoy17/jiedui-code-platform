## 3. 为什么不是直接上传

当前实际后端是 FastAPI/Python，Netlify 原生 Functions 的支持方式为 JavaScript/TypeScript/Go。原有 Python 服务不能作为常驻进程原样放入 Netlify Functions。参考 [Functions 文档](https://docs.netlify.com/build/functions/overview/) 和 [官方语言说明](https://www.netlify.com/blog/2021/04/19/announcing-native-typescript-support-for-netlify-functions/)。

独立代理只扫描当前 `server/app/*.py` 得到：

| 口径 | 静态规模 |
| --- | ---: |
| Python 文件（含注释、空行） | 37 个／12,174 行 |
| `main.py` 挂载的业务 router | 15 个 |
| 挂载 router 的 HTTP 操作装饰器 | 138 个 |
| 额外装饰器 | `/health` 与条件 SPA 路由各 1 个 |
| `store*.py` | 9 个／3,830 行 |
| 源码去重建表声明 | 44 个表名（不是实际数据库表数） |

另有 `assessment_access.py`、`pair_ai_context.py`、`uptake.py` 直接访问 SQL。因此，此次目标要求 API 及存储层迁移，不是仅调整部署文件。没有导入应用、打开数据库或用旧轮次计数代替当前扫描。

## 4. 推荐目标架构与区域

已确认路线：**现有 Vue → Netlify 原生 TypeScript API → 独立 Supabase 新加坡 PostgreSQL 项目**。本轮不再并行引入 Neon，不同时维护两套数据库。

- 前端交由 Netlify CDN；数据库选精确区域 `ap-southeast-1`，不是仅选择宽泛 APAC。参见 [Supabase 区域说明](https://supabase.com/docs/guides/platform/regions)。
- API 尽量与数据库同区域：Netlify 新加坡为 `sin`，东京为 `nrt`。当前官方文档明确自选函数区域需 Pro／Enterprise；账户重新授权后核验实际套餐，不擅自升级。参见 [函数区域与限制](https://docs.netlify.com/build/functions/configuration/#region)。
- 数据库在亚洲不等于请求全链路都在亚洲；API 默认区域、外部模型服务、冷启动和校园网络都会影响延迟。未做实测，不承诺固定毫秒值或“中国大陆一定畅通”。
- 函数和数据库连接秘密只保存在服务端，不进入前端产物。数据库采用适合短生命周期函数的连接方式，并保留真正的事务能力。

## 5. 四项必须迁移的行为

1. **指定人员身份**：现有 `auth.py` 按用户名派生身份，前端 `auth.ts` 网络失败回模拟登录。试用版应使用服务端核验身份与试用成员名单，角色由服务端成员记录决定；线上不能在认证失败时放行本地模拟身份。
2. **数据与并发**：SQLite 的 `?`、WAL、`INSERT OR IGNORE/REPLACE`、`lastrowid`、导入时建表及进程内锁需要替换。PostgreSQL 需迁移文件、唯一约束、条件更新与跨实例事务；不能靠替换连接字符串完成。
3. **可信 AI**：现有代码已经串联生成、授权复核、模型核验和终态回执，不能说它“尚未接入”。但两段模型调用及前端等待不能原封不动塞进有执行上限的函数。Netlify 同步函数上限为 60 秒；需统一时间预算、请求执行租期、幂等与被终止后的状态收敛。若使用后台函数，还需专门设计响应交付、保留期限及自动重试的去重，不能简单打开后台选项就算完成。[官方限制](https://docs.netlify.com/build/functions/configuration/)
4. **学生代码运行**：沿用现有浏览器 Pyodide 真实 Python 路径；C/C++ 的本机编译器及未隔离子进程不能搬入普通业务 API。建议首批明确关闭未具备隔离设施的运行能力，是否接受该范围需用户确认。现有 IDE 已将 mock 标为非真实执行且不形成运行证据，不能误报为现界面把模拟当真实成功。
