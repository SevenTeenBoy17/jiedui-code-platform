## 零、R3 的核心质疑：门禁数字不可复现

R3 §零 指出：此前多轮报告里出现过三个互相打架的「全绿」（233 / 236 / 一次 35 failed 后
又回到 233），并把根因定位在 `server/tests/conftest.py`——固定路径临时库 +
`except OSError: pass`。它据此下了一条很强的判断：

> 在 conftest 修好、并把「clone 基线 3 条失败」查清之前，任何以「pytest 全绿 / 没改坏」
> 为依据的拍板都不成立——包括本报告 §三 里我给出的推荐。

### 我的实测结论：警报**没有复现**，但根因**成立**

| 条件 | 实测结果 |
|---|---|
| 沿用 TEMP 下的脏库（352,256 字节，确认存在） | `236 passed` |
| 干净 TEMP 目录隔离重跑 | `236 passed` |

两种条件同数，**没有复现 R3 说的 35 failed**。此前报的 `233` 是当时的真实数字——
那时 ProgSnap2 的 3 条测试尚未落盘，不是错报，也不是脏库造成的假绿。

但 R3 定位的**缺陷本身是真的**：固定文件名遇上 Windows「连接未关时 remove 必失败」，
会静默沿用上一次的库；并行或多会话跑测试还会互相踩。这是一个**等着咬人的坑**，
只是这次没咬。修它的理由不是「复现了」，而是「门禁数字必须可复现，否则凭它拍的板都不能引用」——
这一条 R3 说得对。

### 修的过程反而暴露了一个更隐蔽的坑

第一版改成无条件 `tempfile.mkdtemp()`——看着是零风险的 5 行改动，结果 `test_assess_probe.py`
从 6 passed 变成 3~5 failed，症状是一批看不懂的 403。

根因：`tests/` 没有 `__init__.py`，conftest 可能被当作第二个模块把模块级代码**重跑一遍**
（`test_learner.py` 顶部的注释早就警告过这件事）。老写法两次导入解析到**同一路径**，
所以二次导入是无害的；换成 mkdtemp 之后，第二次导入把 `store.DB_PATH` 改指到**另一个空库**，
于是夹具写 A 库、请求读 B 库 —— 从「共用一个脏库」变成「分裂成两个空库」。

**教训：改测试基建时，「更干净的隔离」和「导入幂等」是两个正交属性，
只满足前者会把旧写法附带的容错性一并删掉。**

最终写法：认 `JIEDUI_TEST_TMPDIR` 环境变量——导入幂等，且每个 pytest 进程仍是独立目录。

```bash
cd CX/server && PYTHONUTF8=1 .venv/Scripts/python.exe -m pytest
```
现状：三次连跑均 `236 passed`，临时目录零残留。（加上后续 E7 的两条新测试后为 `238 passed`。）

## 一、E8（HIGH）：`req.scaffold` 越权覆盖

### 缺陷
```python
scaffold = req.scaffold if req.scaffold is not None else L.get_state(uid)["scaffold_level"]
```
请求体被无条件采信。学生 token 塞 `scaffold=3` 就能一键取消教师刚下的降档，
而这个被顶掉的值还会被 `_log_reply` 当「服务端权威档位」写进 `ai_reply_log`——
**渐退（本研究的核心自变量）在数据层直接失真**。

### 修法的两次收敛
1. 先按角色判别（教师/研究员才可覆盖）。写测试时发现 `ai.py:186` 的 consent 闸拦的是
   **调用者自己的 uid**，教师根本到不了这个端点——`_may_override` 是永不可达的死代码。
2. 又查到前端 `opts.scaffold ?? null` 恒为 null，从不传值。既然唯一能送出该字段的
   只有手搓请求，就不做角色判别，**无条件忽略**：档位单一权威 = `learner_state`。

字段保留仅为兼容旧前端（收下即丢弃），前端侧同步不再发送。

### 顺带纠正一条被写进测试的错误规范
原 `test_ai_chat_reads_scaffold_from_learner_state` 第 519–521 行把「显式给值即覆盖」
当成规范钉死了——**漏洞行为被测试保护着**。已改写为逐档验证（1/2/3 都不得顶穿），
并补一条反向确认：改库里的档位才算数，证明「拦住了」不是因为整条链没通。

## 二、E7：`save` 埋点的写路径断线

前端 `IdeView.vue:197` 一直在发 `ctApi.track('save', …)`，`ct.py` 的白名单一直不收它；
埋点入口对白名单外类型静默丢弃并返回 `{ok:true}`——**前端以为在采集，DB 里 0 行**。
这是本项目反复出现的「写路径断线」（机制在库、干预不在场）的又一处。

### 对六维公式是惰性的（未触 `ct-rules/v3` 红线）
公式按名字取 `run/error/fix/design_create/ai_help/role_switch`（`_attempts_and_successes`
同理）；`legacy_events` 只统计 `sv<=1` 而新事件都是 `sv=2`。已加测试：刷 20 条 `save`，
`internal_dims` 逐字节不变。

### 但有一处会被动到，必须一起改
`ct_room_participants` 原本是 `SELECT DISTINCT user_id … WHERE room_id=?`，**不挑类型**。
`save` 落库后，「只保存过一次」的学生会进参与者名单，被 `round_snapshot` 冻结出一行
全 0 的六维快照——恰恰是该口径 docstring 明说要排除的情形。

故新增 `store.PARTICIPATION_TYPES` 显式列出参与口径的类型，SQL 按它过滤：
**新增埋点类型默认不进，要纳入必须显式加并说明理由**。否则每加一个类型就悄悄改一次
「谁算参与」，快照口径随埋点演进漂移。
