## B-1 论文定稿措辞（替换 R2 §3.1 讨论章定稿段的第二自然段）

R2 §3.1 现有的定稿段写的是：

> 本研究的渐退作用于**教学型指导的强度**（scaffold_level 0–3 仅调节提示细节量），
> **分析型能力（驾驶员角色的代码生成、沙箱执行、报错回显）全程保留且不随档位下降**。

**在方案B 下这句话是不准确的**，不能这样写。档位段确实无条件拼给两个角色
（`ai.py:115`），驾驶员在 0 档时会同时收到「按学生的指令写关键片段并解释语法」
与「支架强度：最低。只用一两个问题点醒，不给提示细节」两条指令。
准确的替代写法（可直接用）：

> 本研究的渐退作用于**提示细节量**：`scaffold_level` 0–3 四档只改变系统提示中
> 「可给出多少提示细节」的一句约束（0 档「只用一两个问题点醒，不给提示细节」→
> 3 档「可给不超过 3 行的核心 API 示例」），**在任何档位下 AI 均保持在场与可用**，
> 且「绝对禁止直接输出完整、可复制运行的题目答案代码」这一红线在全部四档、
> 两个角色下均原样生效（`ai.py` BASE_RULE）。沙箱执行与报错回显不受档位影响。
>
> 需要如实说明的一处实现限制是：**该档位约束在当前实现中同时施加于驾驶员与领航员两个角色**，
> 而非仅施加于承担教学型指导的领航员。因此本研究的渐退在概念上介于
> guidance fading 与 tool fading 之间，偏向前者（AI 的在场、沙箱与报错回显全程不变，
> 被调节的只是提示的详略），但并非二者的纯粹分离。将档位约束限定于领航员角色
> 是一项已识别的设计改进，因涉及系统提示词版本变更（会使跨版本的回复分类占比不可比），
> 未在本研究的数据收集期内实施。

配套：R2 §3.1 讨论段中「因此该批评所针对的机制在本系统中不存在」这句
**必须降级**为「该批评所针对的核心机制——撤走 AI 的在场与可用性——在本系统中不存在；
但本系统的渐退并未做到指导强度与工具能力的完全分离」。

## B-2 必须同时落地的配套①：把现状钉死成测试

方案B 的风险不是「现在写错」，而是「论文写完后有人顺手改了代码，论文描述变成假的」。
新增 `server/tests/test_ai_scaffold_role.py`（方案B 版本，**与方案A 版本互斥**）：

```python
"""决策1·方案B：把「档位段无条件拼给两个角色」这一**现状**钉死。

论文 §3.1 按现状描述了渐退的作用范围。代码一旦改成「只给 navigator」而论文不改，
论文里那句实现描述就变成了不实陈述 —— 这条测试是它的防线。
改代码的人必须同时看到这条测试红掉，从而知道要回去改论文。
"""
import pytest
from app.ai import ROLE_PROMPT, SCAFFOLD, _system, PROMPT_VERSION


@pytest.mark.parametrize("role", ["turtle", "reviewer"])
@pytest.mark.parametrize("level", [0, 1, 2, 3])
def test_scaffold_segment_applies_to_both_roles(role, level):
    """现状：档位段对 driver 与 navigator **都**生效（论文 §3.1 据此描述）。"""
    s = _system(role, level, None, socratic=False)
    assert SCAFFOLD[level] in s, "档位段未拼给 %s —— 若这是有意的语义变更，" \
                                 "请改用方案A 并同步改论文 §3.1 与 PROMPT_VERSION" % role


def test_driver_at_lowest_level_holds_contradictory_instructions():
    """0 档 driver 同时持有「按指令写关键片段」与「不给提示细节」——
    这是方案B 已知且已在论文中如实交代的实现限制，不是 bug 报告。"""
    s = _system("turtle", 0, None, socratic=False)
    assert "按学生的指令写关键片段" in s
    assert "不给提示细节" in s


def test_prompt_version_unchanged():
    assert PROMPT_VERSION == "ai-prompt/v1", \
        "方案B 的前提是提示词一个字不动；改了就不再是方案B"
```

## B-3 必须同时落地的配套②：manipulation check 的分层报告

方案B 下 driver 与 navigator 的档位剂量相同，因此
`ai_reply_log` 的四分类占比 **必须按 `role` 分层报告**，不得只报总体：
navigator 的档位—四分类曲线是自变量操纵的证据，driver 的那条是「同一剂量下
另一份角色契约的行为基线」。合并报会把两条不同契约的曲线平均掉。

现成可用：`ai_reply_log` 已有 `role` / `scaffold_level` / `socratic` /
`prompt_version` 四列，SQL 一句即可分层，**无需改表**。
注意 `_log_reply` 当前只在 `is_navigator` 时调用（`ai.py:271`），
所以 driver 侧目前**没有**任何回复分类样本 —— 方案B 若要做上述分层，
需要把 `_log_reply` 的调用条件放开到两个角色（这是**采集范围**变更，不是提示词变更，
`PROMPT_VERSION` 不动，但必须在方法章写明起始时点）。
