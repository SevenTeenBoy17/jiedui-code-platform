## 1. 教学模式结构

### 1.1 顶层三方结构（图1，p.49）——与用户模型近乎同构

命名顺序是 **"学生—Agent—教师"**（学生在前），三方权责：

- **学生（Learner）**：主题探索与实践（提问、下达任务）→ 学习成果提交 / 在平台上学习与实践
- **智能体导师（AI Agent Tutor）**：**答疑、编码、评测**（解答、协助编码、反馈）；向下"记录学习数据、生成个性反馈报告"；向上"形成教学改进依据"
- **教师（Instructor）**：设计与引导（组织、干预、监管引导）；配置与管理 Agent 功能；提供教学内容与资源
- **中介层**：教学平台与编程环境（LMS、AI协同编程环境、接口）、教学内容与资源、评价与反馈机制（过程性+反馈性+学习分析）

> 与用户"师—机—生"高度同构，且**"形成教学改进依据"这条 Agent→教师 的箭头明确存在**（p.49 图1），可直接引为"数据回流驱动教师策略"的文献支撑。
> **差异**：谢鑫把"学情感知/学习分析"归入**平台（LMS）**而非 Agent 本身；用户把四职能全归给智能体。谢鑫的切法更接近工程现实（数据采集是平台能力，分析才是智能体能力）。

### 1.2 内容体系三模块（图3，p.50）——渐进式，但非迭代

理论知识模块 → 技能训练模块 → 综合实践模块。
- 理论：编程范式演进（过程式/面向对象/函数式/**Agent式**）、Agent原理（**感知—决策—执行**三层）、提示词驱动的行为控制、大模型协同编码原理
- 技能：语法/数据结构/算法、特征工程数据清洗、AI智能补全与调试辅助、**Prompt 设计迭代训练（意图表达—响应优化—结果评估 三步）**、Pipeline 编程
- 实践：LoRA/QLoRA 微调流程、GGUF 部署、真实行业场景 Prompt 方案、**多Agent协同从原型到功能扩展的全过程开发**、团队系统级方案

> 这是**跨学期的课程序列递进**，不是一个任务内的轮次迭代。**Agent原理"感知—决策—执行"三层结构**（p.50）被当作教学内容教给学生——这是个有意思的元层次：学生要学会 Agent 的工作原理，才能配置 Agent。用户模式可以借这一条把"智能体透明化"写成 K12 版本（让学生知道小狐/小枭为什么这样回答）。

### 1.3 教学策略三环节（图4，p.50）

**自主学习（翻转课堂）+ 智能辅导（个性化与自适应）+ 实践创新（项目任务与AI协作）**
- 自主学习：课前 LMS 微课 → Agent 个性化答疑 → 形成 **"任务—反馈—反思"学习闭环**；必须写学习日志、总结与 Agent 的互动过程（问题/提示词/反馈/改进）并班级分享
- 智能辅导：开发环境侧（代码生成、结构补全、错误定位、调试）+ LMS 侧（智能问答、资源推荐、作业批改、阶段测评）
- 实践创新：**初期技能巩固 → 中期创造性探索 → 后期复杂真实需求（金融风控、智能客服）**

### 1.4 ★ 实施流程：有限的 4周5步（表2，p.53）——本文最关键的"有限性证据"

| 步骤 | 周次 | 活动 | 目标 |
|---|---|---|---|
| 需求分析 | 第1周 | 案例引入 → 讲原理与难点 → 讨论如何用 Agent 改进 → **利用 Agent 头脑风暴，撰写初步项目计划书** | 激发兴趣、理解原理、设计初步方案 |
| 方案设计 | 第2周 | 据反馈完善方案 → 系统设计与知识库构建 → **用 Agent 助手编码、设计数据库表结构、补全前端代码** → **审核与测试生成代码** | 完善设计、掌握设计与编码技能、保证协作与代码质量 |
| 集成开发 | 第3周 | Agent 与系统集成 → 写 API 调用代码 → **Agent 提供伪代码框架与测试问题集** → **教师巡视指导优化提示词** | 实现集成、掌握 API 与数据处理、优化输出 |
| 测试改进 | 第4周 | 系统优化、互测互评 → **解决"Agent 编造知识"等问题** → 设计创新功能（如上下文记忆）→ 生成创新代码 → 整理文档 | 优化功能与准确性、实现创新功能、准备展示 |
| 成果展示与讲评 | — | 展示系统、介绍 Agent 应用与挑战 → 教师点评 → 评分并提交个人总结 | 总结成果、反思收获与不足 |

> **判断**：这是**软件工程瀑布流的教学化**（需求→设计→开发→测试→交付），不是螺旋式迭代。每个阶段只走一次，CT 的分解/抽象/算法/调试各只被练一遍且被绑死在特定周次。
> **这正是用户"三轮螺旋"的优势论证点**：用户的三轮每轮都完整走一遍"分解—建模—实现—调试"，CT 四要素被重复练习并逐轮提升；谢鑫的四周把 CT 四要素切开分配到不同周，学生不会经历"同一问题的第二次分解"。**可写成一句反驳：阶段化 ≠ 迭代化，谢鑫的"有限"是瀑布的有限，本研究的"有限"是螺旋的有限。**

## 2. 智能体架构

### 2.1 ★ 双通道 Agent 架构（1.4.5，p.51-52）——对 CX 最直接可映射的一条

| 通道 | 载体 | 职能 | 数据产出 |
|---|---|---|---|
| **AI 协同编程环境侧 Agent** | 国产平台 Trae / 腾讯云开发平台，典型代表 **Trae 的 MCP（Model Context Protocol）Agent** | ①提示词驱动的代码生成/改写/调试建议 ②多轮交互式编程对话（函数级/逻辑级/模块级）③对接项目目录结构做代码结构优化与模块串联 ④个性化编码效率分析与协同建议 | 代码生成与调试记录 |
| **LMS 侧 Agent** | 超星学习通 AI 助教 / Educoder | 学习监控、反馈生成、辅助测评；对接任务提交，分析**学习路径、交互频率、完成度**；反馈**学习时长、调用情况、知识掌握度**；结合教师标准自动评分 | 学习路径与交互日志 |

**汇聚**："两类数据（代码生成与调试记录、学习路径与交互日志等）最终汇聚至平台，形成统一的多维度学习报告，实现'教—学—评'的数据闭环。"（p.52）

> **这就是 CX 的架构**：学生端 /student/studio + /student/ide（编程环境侧）↔ 教师端教研区（LMS 侧）。谢鑫给了这个双侧架构一个**文献命名**——"双通道 Agent 策略"。CX 目前两侧数据（ct_events、pair 会话、design_create 埋点 vs studies/insights）**还没有"统一多维学习报告"这个汇聚物**，这是可以直接补的产物。

### 2.2 ★ 多 Agent 分工（图5，p.51）——按软件工程生命周期切，不是按教学职能切

```
学生（中心主体）
├─ 需求分析      → 提示词优化 Agent（设计 Prompt 策略）           [LMS平台]
├─ 系统设计/编码 → 代码生成 Agent（快速构建原型框架）             [AI协同开发环境]
├─ 测试验证      → 评测 Agent（静态分析 + 运行测试）              [AI协同开发环境]
├─ 文档与表达    → 文档+PPT 生成 Agent（报告讲解/可视化）          [LMS平台]
└─ 交互日志提交  → 日志分析 Agent（分析学习行为）                 [LMS平台]
教师（过程指导/评审）：监管、引导、反馈
```

> **这是对用户"四职能"切法的一个真正的替代方案**：
> - 用户切法 = **教学功能维**（学情感知/支架推送/学习分析/评价生成）——面向"教与学"
> - 谢鑫切法 = **学科任务维**（需求/编码/测试/文档 + 日志分析）——面向"做什么"
> - 谢鑫的 5 个 Agent 里只有"日志分析 Agent"落在教学功能维，其余 4 个都是**学科工具型 Agent**。
> **对用户的启示**：四职能是正交于学科的（换成写作课也成立），这是优点（普适）也是缺点（没有编程学科味）。可以在"支架推送"职能下**内嵌学科阶段子智能体**（分解期→提问式支架、建模期→数据结构提示、实现期→伪代码骨架、调试期→错误定位提示），这样既保住四职能的教学骨架，又吃到谢鑫的学科贴合度。

### 2.3 技术实现层

- **提示词工程为主**，无 RAG、无工作流编排、无状态机描述。"教师可根据教学任务**预设 Prompt 模板**，引导学生自定义扩展配置"（p.51）
- 学生角色升级路径：**使用者 → 配置者 → 开发者**（"中后期引导学生从使用者逐步转向开发者，基于国产平台（如 Coze、ChatGLM）开展 Agent 定制与多 Agent 协同实践，学习设定行为逻辑与响应机制"，p.51）
- 无自研系统、无接口设计、无数据库设计——**架构描述停在功能框图层，没有工程实现细节**。这是本文最大的短板，也意味着 CX 的工程落地深度**已经超过这篇文献**（这本身是用户论文的贡献点：文献只到框图，本研究到可运行系统）。

## 3. 实施机制细节

### 3.1 任务如何生成下发

- **教师手工 + 周历锚定**（表2 的 4 周 5 步），无智能体自动实例化任务链。
- 唯一的"链"化载体是 **Prompt 模板**：教师按教学任务预设 → 学生在模板上自定义扩展。
- **问题链→任务链的实例化机制在本文缺失**，与 CX 现状（教师手动推送资源）同级。

### 3.2 过程数据如何采集回流

采集项（p.52 表1 + p.53 表3）清单化，可直接抄：

| 数据 | 来源 | 用途 |
|---|---|---|
| **Agent 调用次数/频率** | LMS 自动 | 参与度、依赖度预警 |
| **Prompt 修改轮次** | LMS 日志 | **反思深度的代理指标**（表4 明确标注"体现反思"） |
| **Agent 建议采纳情况/采纳率** | 交互日志 | 人机协作质量 |
| 视频学习时长、测验成绩、交互频率、问题解决率 | LMS 自动 | 进度与掌握水平 |
| 调试日志中错误解决轮次 | 评测 Agent | 编程效率 |
| 代码 Bug 率（每千行） | 评测 Agent 统计 | 代码质量 |
| **日志情绪词汇** | 学习日志文本 | 焦虑/挫败识别 |

### 3.3 ★ 数据回流驱动教师决策——本文唯一被机制化的触发器是"预警"

- p.52（1.5.1②）："LMS 平台自动收集……并**预警**可能的疲劳、焦虑或过度依赖"
- p.51（1.4.4）："结合 **Agent 调用频率、任务完成度与日志情绪词汇**识别学生的过度依赖、学习焦虑或挫败感等倾向，并及时引导与干预"
- p.52（1.5.1④）："教师根据协作日志与互评结果进行**权重校正**"；"及时识别团队协作中存在的问题，如任务分配不均、沟通不畅或个别成员参与度不足等，并据此在教学**中后期调整教学策略**"

> **这是四篇里少见的"可计算触发条件"**：三个信号（调用频率 / 任务完成度 / 日志情绪词）→ 一个动作（预警 → 教师干预）。虽然没给阈值，但**信号集是具体的**，比"数据回流支持教师决策"这种口号强一档。
> 除预警外，其余回流仍是"定期问卷 + 课堂交流 → 调整优化"（1.5.2, p.52-53），**无触发条件、无时点、无产物规格**。结语也自认："适应 AI 协同学习特征的**过程性评价机制尚不完善**，对学习过程与能力成长的量化支持仍显不足"（p.55-56）。

### 3.4 ★ 人机权责边界："助学不代学"的**反向解法**——输出侧问责，不是输入侧限制

谢鑫**明确允许 Agent 直接写可提交的代码**（代码生成 Agent"快速构建原型框架"、"补全前端代码"、"生成创新代码"），它靠**五道过程管理机制**兜底：

1. **强制交互日志提交**："学生需提交完整的交互日志，系统记录其使用评测 Agent、代码生成 Agent 以及反馈分析 Agent 等的过程与效果"（p.51）
2. **规范流程**：教师制定"**何时、如何使用 Agent**"的规范流程（p.51, 1.4.4）
3. **学术诚信检测机制 + 异常提醒**（p.51, 1.4.4）
4. **把人机协作过程质量直接计入分数**：过程性评价 30% 中 "Agent 交互日志分析" 占 10%，指标为"日志内容完整性、任务复杂度、**反思深度**、**Agent 建议采纳情况**"（表1, p.52）
5. **边界认知教学**：课程初期教师示范"Agent 的功能与边界，强调其为**辅助工具而非替代答案**，避免盲目依赖"（p.50, 1.4.1）；测试改进周专门"解决 **'Agent 编造知识'** 等问题"（表2）

> **这是对用户模式的重要补充而非替代**。用户是**输入侧限制**（小枭只提问、苏格拉底锁、不产出可提交代码）；谢鑫是**输出侧问责**（随便用，但全程留痕并计分）。
> 两者可组合成完整论证：K12 认知发展阶段决定必须用输入侧限制（学生尚无判断 AI 输出对错的能力），但输入侧限制**无法自证有效**——仍需输出侧留痕（采纳率、Prompt 修改轮次、日志反思深度）来验证"限制确实转化为了思维参与"。**这一条可以直接补强用户论文"助学不代学如何落地成机制而非口号"的答复。**

## 4. 支架/脚手架：**无渐退机制**（重要缺口确认）

全文**没有任何支架强度递减的设计**。检索到的只有三条隐性渐进线：

| 渐进线 | 方向 | 出处 |
|---|---|---|
| **任务难度递增** | 初期技能巩固 → 中期创造性探索 → 后期复杂真实需求（金融风控、智能客服） | p.51, 1.4.3 |
| **学生对 Agent 的控制权递增** | 使用者 → 配置者 → 开发者（前期教师配置演示 → 中后期学生用 Coze/ChatGLM 定制 Agent、设定行为逻辑与响应机制） | p.51, 1.4.2 |
| **课程序列递进** | 理论知识模块 → 技能训练模块 → 综合实践模块（跨4个学期6门课） | p.49-50, 1.3 |

> **三条都是"加法"，没有一条是"减法"。** 支架从头到尾满强度供给（Agent 全程可用、教师全程巡视）。
>
> **但这里藏着一个对用户模式的尖锐挑战，必须在论文里正面回应**：
> 谢鑫隐含的主张是——**AI 时代不该撤支架，该改变的是学生对支架的支配方式**（从被支配到支配 Agent）。这个主张不是无理的：如果学生毕业后终身与 AI 协同工作，"撤掉 AI"训练的是一种不会出现的工作条件。
> **建议的应对（这是可以写进论文的理论辩护）**：把"渐退"重新定义为**双维**——
> - **维度A（信息量维，用户已有）**：示例支架 → 提示支架 → 仅诊断点拨（**减法**，保证 CT 内化）
> - **维度B（控制权维，借谢鑫）**：智能体预设 → 学生调节支架档位 → 学生自定义智能体提问策略（**加法**，保证 AI 素养）
>
> 两维正交、同步推进：**智能体给出的答案越来越少，学生对智能体的支配越来越强**。这样既守住"助学不代学"，又不违背"AI 时代培养人机协同能力"。**这个双维渐退是用户模式相对四篇文献的一个真正原创点**，且有谢鑫做正面文献支撑（不是硬造）。

## 5. 对用户模型的检验

### 5.1 支持处

| 用户模型要素 | 谢鑫的支撑 | 页码 |

| 师—机—生三方协同 | "学生—Agent—教师"三方协同框架，权责划分几乎同构 | p.47摘要, p.49图1 |

### 5.2 挑战处

1. **智能体职能是"三职能"不是"四职能"**，且"学情感知"被下放给平台而非 Agent。→ 用户需说明：为何学情感知必须是智能体职能而非平台功能？（可答：因为需要智能体做语义级理解，如从对话中判断卡点类型，非平台埋点可得。CX 的 ct_events 六维聚合正好是这个论证的实证。）
2. **智能体直接产出可提交代码**，与"助学不代学"正面冲突。→ 需学段/目标差异化论证：谢鑫的目标3明确要求"开发时长缩短20%以上"（p.48），效率是教学目标；CT 导向的 K12 教学中，效率不是目标，思维过程才是。
3. **无支架渐退**，且隐含"控制权递增"这一反向主张（见 §4）。→ 用户必须正面回应"AI时代为什么还要撤AI"。
4. **三轮迭代不存在**：谢鑫是瀑布分段（需求→设计→开发→测试→展示），每个 CT 要素只练一遍。→ 反过来成为用户"螺旋三轮"的优势论证。
5. **CT 几乎不被测量**：目标1 提了"计算思维能力"，但表4 的实测指标是项目完成度、Bug率、创新功能数、Prompt修改轮次、主动性自评——**没有一个是 CT 维度**。→ 用户"CT导向"的定位在这篇里是空白，是差异化空间。
6. **评价三方错位现象**（图8, p.55）：学生自评偏低 < 同伴互评中等 < 教师校正得分更高。→ 提醒用户：如果模式里有自评/互评，需设计一致性校正机制，否则数据不可用。

### 5.3 有无更好的替代切法

有一个值得认真考虑的：**"通道维 × 职能维"二维切分**。
- 谢鑫用**通道**切（编程环境侧 Agent / LMS 侧 Agent），用户用**职能**切（四职能）。
- 二者可交叉：学情感知与支架推送主要发生在**学生侧通道（IDE/结对页）**，学习分析与评价生成主要发生在**教师侧通道（教研区）**。用户的模式图如果在四职能上再叠一层"面向生 / 面向师"的通道归属（图1已有"对师输出/对生输出"两条边，只差把四职能挂到边上），结构会更清楚，也更贴合 CX 实际的前后端边界。

## 6. 可落到 CX 的具体工程（对着四个已知缺口）

### 缺口① 支架渐退无实现
- **双维渐退**落地：
  - 维度A（信息量）：`backend/app/routers/ai.py` 的 `scaffold` 参数从"教师手调"改为**由 round 派生**——round=1 允许示例代码片段、round=2 只给结构提示/伪代码骨架、round=3 只给诊断问句。在 `build_system_prompt` 里按 round 注入不同的禁令强度（复用现有 `ai_navigator` 的反越狱规则写法）。
  - 维度B（控制权）：round=1 用平台预设 persona；round=2 前端暴露"支架档位"滑杆给学生自选（并埋点记录学生选了几档——**学生主动降档次数本身就是自我调控的证据**）；round=3 开放"自定义小枭提问策略"的模板槽位（对应谢鑫的"使用者→配置者"）。
- 借谢鑫的**Prompt 模板机制**：教师端预置 Prompt 模板 + 学生可改写槽位，天然是维度B的载体。

### 缺口② 任务链无实现
- 按谢鑫的经验，任务链的最小可行载体是**"任务卡 = 问题链条目 + 智能体实例化的 Prompt 模板 + 可改写槽位 + 完成判据"**。
- 新增 `task_chain` 表（study_id / round / seq / problem_ref / prompt_template / slots / done_criteria / scaffold_level），教师侧维护问题链，智能体依 ct_events 学情把问题链条目实例化为该生的任务卡序列。
- 阶段推进的**触发条件**可抄谢鑫的两条：①完成判据达成（任务完成度）②周次到点（周历锚定）——**双触发（能力 OR 时限）比纯能力触发好落地**，避免个别学生卡死在 round 1。

### 缺口③ 三轮迭代在平台无对应结构
- 关键洞察：`studies` 的 `pretest/running/posttest` 是**研究阶段**，与教学**轮次**正交，不该复用。应新增独立的 `round` 维度（1/2/3）挂在班级/任务上，`ct_events` 增加 `round` 字段，所有埋点携带轮次。
- 谢鑫的"4周5步"给了低成本实现路径：**round 绑定课时/周次**（第1-2课时=round1 分解建模、第3-4=round2 算法实现、第5-6=round3 综合优化），教师端一键推进轮次，不必做复杂的自适应判定。
- 教师端"今日/课堂监看 live"加一个**轮次指示条**，显示本班当前轮次 + 各生轮内进度。

### 缺口④ 数据回流→教师策略调整无闭环
- **直接抄谢鑫的三信号预警**：`Agent 调用频率`、`任务完成度`、`日志/对话情绪词` → 阈值超限 → 教师告警。**CX 已有 R5 的教师告警端点（安全事件落库 + 告警）**，扩展一个 `alert_type=learning_risk` 复用同一通道即可，工程成本极低。
- **新增两个埋点指标**（谢鑫已验证有区分度）：
  - `prompt_revision_rounds`（学生改写提问的轮次，谢鑫实测均值 3.6 次，作为"反思深度"代理）
  - `ai_suggestion_adoption_rate`（智能体建议采纳率，反映依赖度 vs 批判性）
  - 两者接入 `ct.py` 六维聚合，作为"调试评估"维与新的"人机协同"维的观测项。
- **补一个 CX 目前缺失的产物**：谢鑫的"统一多维度学习报告"。CX 的 `insights.py` 结论卡 + `study.py` 对比报告已有半成品，缺的是**把 IDE 侧（design_create/运行/调试）与教研区侧（studies/画像）两路数据合并成一份"教—学—评闭环报告"**，并在报告尾部给教师**三条可执行的策略建议**（这就是"数据回流→策略调整"的闭环产物，把口号变成一个具体文件/页面）。

## 7. 可直接引用的论点（含页码）

- **三方协同结构**："构建一种融合自主学习、智能辅导与实践创新的'学生—智能体—教师'三方协同教学模式"（谢鑫等, 2026, p.47）
- **数据闭环**："两类数据（代码生成与调试记录、学习路径与交互日志等）最终汇聚至平台，形成统一的多维度学习报告，实现'教—学—评'的数据闭环"（p.52）
- **智能体边界的教学化处理**：教师在课程初期示范引导学生理解 Agent 的功能与边界，"强调其为辅助工具而非替代答案，避免盲目依赖"（p.50）
- **过程留痕问责**：学生须提交完整交互日志，教师"据此分析其规范性、效率与优化策略并给予指导"（p.51）；交互日志分析在评价体系中占 10%，指标含"反思深度、Agent 建议采纳情况"（表1, p.52）
- **依赖风险的可计算信号**：结合"Agent 调用频率、任务完成度与日志情绪词汇"识别过度依赖、学习焦虑或挫败感并及时干预（p.51）
- **过程性评价的自认缺口（可用于论证本研究必要性）**："适应 AI 协同学习特征的过程性评价机制尚不完善，对学习过程与能力成长的量化支持仍显不足"（p.55-56）；未来需"'AI 素养—任务表现—协同能力'一体化评价框架"（p.56）
- **学生角色升级路径**：中后期引导学生"从使用者逐步转向开发者"，开展 Agent 定制与多 Agent 协同实践（p.51）
- **实证效果**：项目完成度 78.4→89.1（+13.7%），Bug 率 4.2→2.5 每千行（-40.5%），创新功能数 0.7→1.3（+85.7%），任务主动性 3.1/5→4.4/5，平均 Prompt 修改轮次 3.6 次（表4, p.55）
- **有限阶段实施**：4 周 5 步（需求分析/方案设计/集成开发/测试改进/成果展示）（表2, p.53）

## 8. 研读思考痕迹（给自己/给论文写作用）

1. **对用户"四篇只画无限闭环"这一判断的修正建议**：谢鑫是"模式图无限闭环 + 实施表有限线性"。写论文时不要说"文献没有有限性设计"（会被证伪，表2就是反例），应说"**已有模式将阶段有限性降级为实施细节，未将其上升为模式的结构要素，因而无法在模式层回答'迭代到第几轮该收敛'的问题**"。这个说法既精确又保住了差异化。
2. **谢鑫的最大方法论贡献不是模式，是"过程留痕即评价"**。他把"人机协作过程"本身变成了 30% 的分数，这是把"助学不代学"从道德要求变成了制度激励。用户的苏格拉底锁是"禁止"，谢鑫是"计分"——**禁止 + 计分 才是完整机制**。
3. **谢鑫的多 Agent 是"工具型多 Agent"，用户的是"教学型多 Agent"**——这个区分值得在文献综述里明确写出来，是一个干净的分类维度：按学科任务切 vs 按教学职能切。四篇文献可以用这个维度重排。
4. **本文的工程深度低于 CX**。全文没有一处系统实现细节（无接口、无数据结构、无算法），Agent 全是商业产品（Trae、超星、Coze）的组装。**这意味着用户论文里"自研平台+可运行系统+埋点数据"是相对本文的绝对优势**，应在贡献陈述里强调。反过来说，本文的"6门课4学期微专业"课程体系建设厚度是 CX 没有的，用户不必在这方面对标。
5. **一个可能被审稿人问的问题，先备好答案**：谢鑫用 4 周对应 4 个软件工程阶段，周次即阶段，非常自然；用户的"三轮"如果不绑课时，凭什么是三轮而不是二轮/四轮？**建议在论文中给出三轮的划分依据**——可对应 CT 的认知负荷递减规律，或对应"分解建模→算法实现→综合优化"这三类质变（而非量变）任务，并说明第三轮后进入"数据回流·反思迁移"是因为**支架已降至零（仅诊断点拨），再迭代无支架可撤**。这个"以支架撤尽为收敛条件"的论证，恰好把"渐退式支架"和"有限三轮"两个创新点绑成一个逻辑，比两个孤立的创新点强得多。**这可能是本轮研读最大的收获。**

## 苏格拉底追问（第二波 · 模式检验专场）

> 本节不复述研读结论，只做一件事：**对每个看起来已经成立的主张追问三层——依据是什么／换到"初中+结对编程+CX"还成立吗／最弱环在哪**。
> 追问对象既包括谢鑫，也包括**用户自己的顶层模式图**。凡出现 ⚠️ 的，是必须在论文里正面处理、否则会被审稿人击穿的点。

---

### 追问链 A：⚠️「三轮」的轮名暴露了它其实是瀑布——本轮最尖锐的发现

**A1. 问：用户批评谢鑫"4周5步是瀑布的有限，不是螺旋的有限"，这个批评站得住吗？**
站得住——谢鑫需求→设计→开发→测试各走一次，CT 四要素被切开绑死在不同周次。

**A2. 再追问：把这把刀掉过头砍用户自己的图，会砍中吗？**
**会，而且砍得很深。** 用户的三轮命名是 `第一轮·分解建模 → 第二轮·算法实现 → 第三轮·综合优化`。与谢鑫对齐看：

| 用户三轮 | 谢鑫四周 | 是否同构 |
|---|---|---|
| 第一轮·分解建模 | 第1-2周 需求分析＋方案设计 | ✅ 几乎同义 |
| 第二轮·算法实现 | 第3周 集成开发 | ✅ 同义 |
| 第三轮·综合优化 | 第4周 测试改进 | ✅ 同义 |

**轮名本身就是阶段名。** 若第一轮只做分解建模、第二轮只做算法实现，则"每轮完整走一遍分解—建模—实现—调试"这句宣称在图上**没有任何结构支撑**，反被轮名直接否定。这是**用户模式图内部的自相矛盾**：外圈三轮徽章写的是阶段序列，中间却宣称是螺旋。审稿人只要并排读这两处，差异化点当场瓦解——"你批评人家瀑布，你自己也是瀑布，只是把'周'改叫'轮'"。

**A3. 再追问：怎么救？** 二选一，必须写清楚：

- **路线 1（推荐，改轮名保结构）**：轮次的区分维度改为**制品完成度/质量层级**而非 CT 要素：
  `第一轮·能跑（最简可运行原型）→ 第二轮·跑对（覆盖边界与正确性）→ 第三轮·跑好（优化与迁移）`
  每一轮都完整经历"分解→建模→实现→调试"，只是每轮分解的**粒度**、建模的**抽象层级**、调试的**判据严格度**在提升。这才是真螺旋（Boehm 螺旋的教育学移植），也才配得上"同一问题的第二次分解"这句反驳。
  **附带红利**：三轮的划分依据不再需要外部理论硬凑——"能跑/跑对/跑好"是编程活动本身的自然三层，初中生也听得懂，且与渐退支架天然对齐（能跑阶段最需示例支架，跑好阶段只需诊断点拨）。
- **路线 2（保轮名改宣称）**：承认三轮是 **CT 要素的重心迁移**而非完整重走，宣称降级为"每轮以某一 CT 要素为**主导**，其余三要素**伴随**"，图上用主/辅深浅色标出。这条路诚实但**丢掉对谢鑫的差异化**——谢鑫同样可以说他每周都伴随其他要素。

**暂时的答**：**必须走路线 1。** 否则"螺旋 vs 瀑布"这个最有力的差异化论证会被自己的轮名反噬。

---

### 追问链 B：「有限三轮」的收敛依据是什么？会不会是循环论证

**B1. 问：为什么是三轮而不是二轮/四轮？**
§8.5 给了一个漂亮答案：**以"支架撤尽"为收敛条件**——支架三档（示例→提示→仅诊断），撤到零即收敛，故三轮。

**B2. 再追问：这是论证还是循环？**
⚠️ **接近循环。** 支架为什么三档？因为三轮。三轮为什么是三？因为支架三档。两个变量互相定义，没有一个锚在外部。审稿人一句"支架为什么不是四档"即可戳穿。

**B3. 再追问：外部锚可以是什么？** 三个候选，按可辩护性排序：
1. **制品质量三层（能跑/跑对/跑好）**——来自编程活动本身，最硬，与追问链 A 路线 1 同源。**支架档位由轮次目标派生，而不是反过来。**
2. **课时结构**——抄谢鑫的"周历锚定"：初中信息科技单元常见 6 课时，2 课时一轮正好三轮。最好落地（CX 直接 round 绑课时），但**只是行政依据不是认知依据**，只能作辅助论据。
3. 认知负荷递减/最近发展区——听着高级，但**无法量化、无法证伪**，写进去反而会被要求给证据。**不建议作主依据。**

**B4. 再追问：三轮结束学生还没达标怎么办？"有限"会不会变成"放弃"？**
⚠️ 这是"有限迭代"最易被质疑为反教育之处。
**答**：必须说清有限性的**作用域**——**三轮是"一个问题单元内"的有限，跨单元仍是无限螺旋**，即"**有限内嵌于无限**"。单元内三轮收敛，保证支架必然撤尽、避免无限依赖；跨单元轮次重置但起点抬高（第二单元 R1 的支架强度低于第一单元 R1）。
这样既保住"显式有限"的差异化，又不背"三轮之后不管学生死活"的锅。**建议直接画进模式图外圈——在"数据回流·反思迁移"箭头旁标注"→ 次单元 R1（支架基线上移）"。**

---

### 追问链 C：⚠️「AI 时代为什么还要撤 AI」——谢鑫的反向主张必须正面回应

**C1. 问：双维渐退（信息量做减法 + 控制权做加法）够不够？**
方向对，但**还差一层**。"智能体给出的答案越来越少，学生对智能体的支配越来越强"很漂亮，但审稿人会问：**这两维凭什么同步？** 万一学生拿到"自定义提问策略"权限后第一件事就是把小枭改成小狐（领航员改驾驶员），控制权的加法直接抵消信息量的减法。

**C2. 再追问：换到初中生还成立吗？**
⚠️ **控制权维在初中最脆弱。** 谢鑫的"使用者→配置者→开发者"是**大三软件工程微专业**，学生能写 Coze 工作流。初一学生"自定义智能体提问策略"的现实上限大概只到**从教师给的 3-5 个提问风格模板里选一个**（"多给例子的小枭"／"只问为什么的小枭"）。把大学生能力曲线直接搬到初中是硬伤。
**答**：控制权维在 K12 必须降级为**"受约束的选择权"**而非"开发权"：
`R1 平台预设 → R2 学生在教师白名单档位间自选（可升可降，全埋点）→ R3 学生从模板槽位组装提问策略（槽位有值域约束，不可跨越"不直接给代码"的硬红线）`
关键设计：**控制权上限被"助学不代学"硬约束封顶**——学生可以调"给多少提示"，但不能调"给不给答案"。这条红线必须写进论文，否则双维渐退看起来像给学生开后门。

**C3. 再追问：CX 有一个谢鑫完全没有的东西，能给"撤 AI"更好的辩护吗？**
**能，这可能是全篇最强的原创点：CX 有真人结对。**
谢鑫是"学生 ↔ Agent"二元，撤了 Agent 学生就孤立无援，所以"撤 AI"在他那里确实不合理。CX 是"学生 ↔ 同伴 ↔ Agent"三元——**支架不是被撤销，是被转移**：

| 轮次 | AI 支架 | 同伴支架 | 自我支架 |
|---|---|---|---|
| R1 能跑 | 强（示例） | 弱（角色刚熟悉） | — |
| R2 跑对 | 中（提示） | **强（领航员承接质疑职能）** | 弱 |
| R3 跑好 | 弱（仅诊断） | 中 | **强（自我提问/自查表）** |

一句话辩护：**本模式撤的不是"人机协同"，而是"人机协同中机器的答案供给"；协同强度不降，支架的承担者从 AI → 同伴 → 自身逐级内化。** 这既回应谢鑫"AI 时代不该撤 AI"，又把 CX 的结对特性从"一个功能"升级成"模式的理论承重墙"。
⚠️ **落地前提**：CX 目前 PairDock 的小狐/小枭是 AI 角色，真人 driver/observer 是另一套（collab.py）。**两套角色体系必须在模式图上明确区分**，否则"同伴承接领航职能"只是纸上的话。

### 追问链 D：四职能切法的最弱环是「学情感知」

**D1. 问：谢鑫把学情感知给了平台（LMS）而非 Agent，用户凭什么坚持它是智能体职能？**
笔记 §5.2.1 的答复是"需要语义级理解（从对话判断卡点类型），非平台埋点可得"。

**D2. 再追问：CX 现状支持这个答复吗？**
⚠️ **不支持，反而反证。** CX 的"学情感知"当前落地 = `teacher/live` + `ct_events` 埋点——**这恰恰是平台埋点，不是智能体的语义理解**。用户在论文里主张"学情感知是智能体职能"，自己系统里它却是平台职能。**这是模式与实现之间的硬性不一致，审稿人看系统截图就会发现。**

**D3. 再追问：怎么补？** 两条：
- **工程上补实**：让"学情感知"真的产出**只有智能体能产出的那部分数据**——从结对对话/AI 对话里抽取**卡点类型标签**（需求没读懂／分解不到位／算法想错／语法错但归因错／已放弃求答案），写回 ct_events。这才是"语义级"，埋点做不到。
- **模型上说清**：把学情感知拆成**信号层（平台埋点）+ 解释层（智能体语义标注）**，四职能里的"学情感知"专指解释层。既承认谢鑫的工程现实（采集是平台能力），又保住智能体职能的正当性。**建议图上改标为"学情感知（解释）"或在职能框内加一行小字。**

**D4. 再追问：四职能还有别的弱环吗？**
有一个结构性的：**四职能是纯教学功能维，正交于学科，"编程"在这张图里可被替换成任何学科而不影响成立**。这是普适性优点，也是"这凭什么是一张*编程*教学模式图"的软肋。
**答（吃谢鑫的学科贴合度而不破坏四职能骨架）**：在"支架推送"职能下内嵌**学科阶段子策略**——分解期→提问式支架、建模期→数据结构/表征提示、实现期→伪代码骨架、调试期→错误定位提示。四职能仍是骨架，学科味挂在支架推送这一根骨头上。
**另接受 §5.3 的"通道维"改造**：把四职能挂到已有的两条输出边（学情感知＋支架推送→对生边；学习分析＋评价生成→对师边）。这个改动**零成本纯收益**：图更清楚、与 CX 前后端边界同构、顺手回答"为什么恰好是四个"（每条边两个，2×2 结构化，比四个并列更难被问）。

### 追问链 E：「任务链由智能体依学情实例化」——是机制还是措辞？

**E1. 问：这句宣称目前有什么支撑？**
⚠️ **零支撑。** 谢鑫这里也是空白（教师手工＋周历锚定，唯一"链"化载体是 Prompt 模板）；CX 现状同级（教师手动推送资源）。**两边都空，意味着这是可以真正原创的地方，也意味着写不实就是空话。**

**E2. 再追问：最小可信的"实例化"是什么？什么程度会被判为"只是填模板的 CMS"？**
判据很简单：**同一条问题链条目，对两个不同学情的学生，产出的任务卡必须可见地不同**。做不到，"智能体实例化"就是给 CMS 换名字。
最小可信实现（三输入 → 一张任务卡）：
```
输入：问题链条目（教师制品，含目标 CT 要素）
    + 该生 ct_events 近期画像（卡点类型 / 六维弱项 / 上轮 done_criteria 达成情况）
    + 当前 round（决定 scaffold_level 与 done_criteria 严格度）
输出：任务卡 = 子问题表述（措辞按弱项调整）
              + 实例化后的 Prompt 模板（含学生可改写槽位）
              + 完成判据（可机判：运行通过 / 用例覆盖 / 自查表勾选）
              + 支架档位（由 round 派生，学生可在白名单内下调）
```
**"任务卡在两个学生之间可见地不同"应作为论文里的一张对比图**——把"实例化"从措辞变成证据的最省力做法。

**E3. 再追问：推进触发条件用什么？纯能力判据会不会卡死？**
抄谢鑫的**双触发**：`done_criteria 达成 OR 课时到点`（能力 OR 时限，取或不取与）。纯能力触发会让弱生永远停在 R1；纯时限触发退化成谢鑫的周历瀑布。
⚠️ **双触发的副作用必须承认**：被时限推进的学生，其支架撤退并非建立在已内化之上——**撤支架反而可能造成伤害**。
**补丁**：轮次推进用双触发，**但支架档位跟随的是"判据达成度"而非"轮次"**：`scaffold_level = f(round, done_rate)`，被时限推上 R2 但 R1 判据未达成者保留 R1 支架强度（图上称"支架滞后一轮"）。这一条很小，却把"渐退式支架"从**齐步走**改成**个体化**，是四篇文献里没有的。

### 追问链 F：数据回流的产物规格——口号与机制的分界线

**F1. 问：怎么判断"数据回流→教师策略调整"是机制还是口号？**
操作性判据：**说得出触发条件、时点、产物规格三样，才算机制。** 谢鑫只有"预警"凑齐了触发条件（三信号）与动作（教师干预），其余全是"定期问卷+课堂交流"，缺时点与产物。用户目前四样都缺。

**F2. 再追问：CX 最省力的补法？**
- **触发条件**：抄三信号，但**换成初中结对场景的等价物**——谢鑫"Agent 调用频率"→CX"向小狐/小枭提问频次"；"任务完成度"→done_criteria 达成率；"日志情绪词"在初中要谨慎（易误判、涉学生心理数据），**建议替换为行为信号**：`连续无进展时长` ＋ `结对中沉默/被动方占比`（后者是 CX 独有、谢鑫没有的强信号）。
- **时点**：轮次结束时必触发一次（而非"定期"）。
- **产物规格**：**轮次闭环报告**，尾部必须有**三条可执行策略建议**，每条绑定一个可操作对象（哪几个学生／下一轮哪个问题链条目要改／哪个支架档位要调）。
⚠️ **关键判据**：报告若不能改变"下一轮任务链的实际内容"，闭环就没闭。**建议回流产物直接写成"下一轮问题链的差异化修订建议"，教师一键接受即写入 task_chain。** 这样"数据回流"在系统里有一条可追踪的**写路径**，而不只是一个可视化页面。

### 追问链 G：「助学不代学」——禁止能不能自证有效

**G1. 问：苏格拉底锁（输入侧限制）足够吗？**
不够。⚠️ **输入侧限制无法自证有效**——锁住 AI 不给代码，不等于学生真的在思考，也可能是转去别处抄、或干脆放弃。

**G2. 再追问：谢鑫的输出侧问责能直接搬吗？**
部分能。谢鑫"把人机协作过程质量计入 30% 过程性分数（交互日志 10%，指标含反思深度、建议采纳情况）"把道德要求变成制度激励，**思路可搬，指标要换**：
- 可搬：`prompt_revision_rounds`（改写提问轮次，谢鑫实测均值 3.6，作反思深度代理）、`ai_suggestion_adoption_rate`（采纳率，反映依赖 vs 批判）。
- 要换：谢鑫的"代码 Bug 率/千行""开发时长缩短 20%"是**效率指标**，与 CT 导向的 K12 目标冲突，**不能抄**（抄了等于承认效率是教学目标，自己拆自己的台）。
- 要新增（CX 独有）：`结对话轮均衡度`、`领航员提问质量`——谢鑫没有结对，这两项是纯增量。

**G3. 再追问：合起来怎么说？**
**"输入侧限制 + 输出侧留痕 + 过程计分"三件套**：限制（苏格拉底锁）保证 AI 不越界；留痕（采纳率/改写轮次/结对话轮）保证限制的效果可被**验证**而非假设；计分（把人机协作过程质量纳入任务卡完成判据）保证学生有动机走"思考"这条路而非绕过。
**一句话（可直接进论文）：禁止解决"AI 会不会代学"，计分解决"学生会不会真学"；缺任一半，"助学不代学"都只是口号。**

### 追问链 H：对"四篇均只画无限闭环"这一差异化陈述的最后压力测试

**H1. 问：谢鑫的表2 是反例吗？** 是。所以"文献没有有限性设计"**会被一条表格证伪**。

**H2. 再追问：修正后的措辞（"有限性被降级为实施细节，未上升为模式的结构要素"）就安全了吗？**
⚠️ **还不够。** 审稿人的下一问是：**"把它画到模式图上，除了图更好看，带来了什么？"** 徽章本身不是贡献。

**H3. 再追问：那什么才是贡献？**
只有当**三轮各自携带可区分的机制**时，显式化才有意义。检查表（论文里应逐项给出，缺一项差异化就弱一分）：

| 维度 | R1 | R2 | R3 | 现状 |
|---|---|---|---|---|
| 制品目标 | 能跑 | 跑对 | 跑好 | ⚠️ 待改（当前是阶段名） |
| AI 支架档位 | 示例 | 提示 | 仅诊断 | ✅ 已有 |
| 学生控制权 | 预设 | 白名单自选 | 槽位组装 | ✅ 已有（需 K12 降级） |
| 支架承担者 | AI | 同伴 | 自身 | ★ 新增（CX 结对独有） |
| 完成判据严格度 | 运行通过 | 用例覆盖 | 自查表+迁移题 | ⚠️ 待补 |
| 评价重心 | 参与 | 正确 | 反思迁移 | ⚠️ 待补 |
| 教师角色 | 示范 | 巡视 | 退位为评审 | ⚠️ 待补 |
| 推进/收敛触发 | 判据 OR 课时 | 同 | 同→回流 | ⚠️ 待补 |

**暂时的答**：**差异化不在"画了三轮"，而在"三轮之间有八条可区分的机制变化，且每条在系统里都有对应实现"。** 这句话既守住原创性，又不会被一条表格证伪。**建议把上表原样做成论文的一张核心表——它同时是模式说明、系统设计说明和差异化论证。**

### 本轮追问的最终收敛

1. **必须改**：三轮轮名（分解建模/算法实现/综合优化）与"螺旋"宣称自相矛盾，实为瀑布换词。改为制品完成度三层（能跑/跑对/跑好），每轮完整走一遍 CT 四要素。
2. **必须补**：三轮的收敛依据不能靠"支架三档"循环论证，外部锚 = 制品质量三层（主）+ 课时结构（辅）。
3. **必须说清**：有限性的作用域是"单元内有限、跨单元无限"，避免被读成"三轮后放弃学生"。
4. **必须回应**：谢鑫的"AI 时代不撤 AI"。最强辩护不是双维渐退本身，而是**CX 的三元结构使支架得以转移而非撤销**（AI→同伴→自身）——这是相对四篇文献的真正理论增量。
5. **必须补实**：学情感知在 CX 现状里是平台埋点，与"智能体职能"的主张不一致。补法 = 卡点类型语义标注写回 ct_events，并把职能拆成信号层/解释层。
6. **免费收益**：四职能挂到"对师/对生"两条边上（2×2），图更清楚且顺带回答"为什么是四个"。
7. **一句话把口号变机制**：任务卡在两个不同学情的学生之间可见地不同；回流报告能一键写回下一轮任务链；禁止＋计分同时在场。
